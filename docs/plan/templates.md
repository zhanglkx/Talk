# 模板与 Review 清单

## 1. 技术设计模板

每个功能编码前填写，写在当周文档的「技术设计」一节。只写要点，不写代码；评审通过后再动手。

数据

- 要存哪些数据？每个字段的类型、是否必填、长度或取值范围？
- 哪些字段必须唯一？只在代码里检查，还是数据库也有约束？为什么？
- 和哪些已有数据关联？被关联的那条数据停用或删除时，这条数据怎么办？
- 删除是真删除，还是保留记录（停用、软删除）？为什么？

接口

- 列出接口：方法 + 路径、请求参数、成功响应、可能的错误（状态码和原因）。
- 谁能调用？能看到、改动哪些数据？

规则与边界

- 有哪些业务规则？每条规则分别在哪一层检查（前端、后端、数据库）？
- 两个人同时操作同一条数据会怎样？同一个请求被重复发送会怎样？

前端

- 页面有哪些状态（加载、空、错误、无权限）？
- 操作失败时用户看到什么？

本周故意不做

- 写下你意识到、但本周不处理的问题，以及打算在哪一周解决。

## 2. 复盘模板

每周最后填写，写在当周文档的「复盘」一节。

- 实际用时：__ 小时（对照当周文档的预计）
- 本周 3 个核心概念：用自己的话各写 2～3 句，说清它解决什么问题、不用会怎样。
- 卡得最久的地方：原因是什么，最后怎么解决的。
- 下周想先弄明白的一件事。

面试题直接答在当周文档的题目下面。

## 3. Code Review 清单

助手看自上次 Review 以来的提交（`git diff <上次 Review 的提交>..HEAD`），按下面的顺序检查。只检查[企业级清单](README.md#五企业级清单)里已到周次的条目；当周文档「本周故意不做」里列出的内容，不作为 Review 意见。

1. 需求：验收标准是否逐条满足？有没有做需求以外的东西？
2. 正确性：边界值、空值、重复请求、并发；每条错误路径是否都有处理？
3. 安全：身份只来自服务端校验过的 token；不信任前端传来的用户 ID、角色和总金额；权限在后端检查。
4. 分层：Controller 只负责接收和返回，业务规则在 Service；Controller 不直接访问数据库，查询复杂时再抽出单独的 Repository 类；前端组件里不散落接口地址和请求细节。
5. 数据：改表有 migration；数据库约束兜底；金额和时间的类型正确。
6. 可读性：命名表达业务含义；一个函数只做一件事；注释说明"为什么"，不复述代码做了什么。
7. 测试：关键规则有测试；测试名说清场景和期望结果。
8. 提交：一次提交只做一件事，提交信息说明为什么。

意见分三档：

- 必须改：会导致错误、安全问题，或违背已定的规则；不改的话这次 Review 不算通过。
- 建议改：更易读、更好维护的写法；本周或下周改。
- 可讨论：有几种合理做法，说出你的理由即可。

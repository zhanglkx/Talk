## 一、部署拓扑与边界

单实例：浏览器 → HTTPS反向代理（静态Web、/api/v1）→ loopback Nest API → 私有PostgreSQL。应用迁移与运行读同一个DATABASE_URL配置键，可由独立进程注入不同权限凭据。

采用非Docker运行环境；CI的真实PostgreSQL用GitHub托管Ubuntu runner预装的PostgreSQL（默认不启动，作业里先sudo systemctl start postgresql.service再建专用库），或受控专用实例；不用Actions的services:（那是Docker容器），不复用开发/默认postgres库。测试删除前执行库名/主机允许校验。

SESSION_SECRET/可信APP_ORIGIN/模型未来密钥由部署秘密注入，不写真实值到.env.example。Cookie Secure开启；代理trust范围限定，不能信任任意X-Forwarded头。

业务上线前分离公共Swagger和内部ready：公共文档/前端类型排除内部路径或单独内部产物；反向代理白名单是实际暴露边界，不靠文档排除实现安全。

## 二、CI门禁与工具命令

现有pnpm check=contracts→typecheck→根pnpm test→build，根pnpm test先跑API测试再跑Web（M1-S12）；真实库集成测试是单独的test:db（M1-S10），不在check中；没有lint、开发库migration脚本、E2E。新增检查必须先建立实际package scripts和配置，再加CI。

建议流程：锁文件安装→提供有效非秘密DB URL/认证测试配置→普通检查→在独立库显式migrate→真实DB/HTTP/E2E→build。contracts允许合法但不可达URL、不得隐式迁移。

contracts会改生成文件，所以CI在生成后比较docs/openapi.json与Web api-types的Git diff，新鲜度不符失败。secret不能输出完整环境。

lint使用项目统一规则，先校验引入影响，避免阶段顺带重排全仓库。CI失败保留错误，不关闭安全/事务用例。

## 三、日志、指标与故障定位

入站请求ID验证长度/字符，不可信任客户端ID进行身份授权。反向代理/API传播已验证requestId；在中间件完成事件记录Guard/Pipe拒绝也能追踪。

允许日志：route模板、status、durationMs、error.code、匿名用户键、DB错误类别/池使用数。禁止原始SQL参数/完整body、SID、password/hash、DATABASE_URL。

关注5xx/503比例、HTTP p95、连接池与慢查询、锁等待。先做结构化stdout+轻量统计，不引入大型日志平台。用授权本地fixture故障产生503并追踪一例。

ready继续status:ready/not_ready；业务统一error信封，不让Filter改探针语义。最大语句/锁/连接等待与HTTP总时长应有界，取消或超时后回滚释放资源。

## 四、迁移发布与备份恢复

发布顺序：记录revision/迁移版本→备份（尤其破坏性变更）→独立显式迁移→启动新版→内部ready→业务/浏览器烟测。应用账户不获得无必要DDL权限。

使用本机pg_dump/pg_restore或同等PostgreSQL工具，备份存隔离目录，不入Git。恢复目标必须专用空库；确认PG版本、schema/migration历史及seed策略，不能在恢复后重复seed覆盖密码。

恢复验收核对用户隔离、流水数/软删数、独立SQL月报、首次创建快照重放；只看restore退出0不够。记录耗时、备份时间与可恢复窗口，不伪称RPO/RTO已达SLA。

migration down仅可在可丢弃测试库演练；若迁移损坏已有数据，优先前向修复或经审批恢复，不把git rollback/down等同恢复全部数据。

## 五、观测与验证

HTTPS实际浏览器检查Cookie、CSRF、防缓存与同源；公网/internal/ready应被拒绝且PostgreSQL端口不可达。授权目标仅自己的预览环境，不做外部扫描。

测试硬件、记录数、查询、并发、预热/样本量、p50/p95与错误率；本机M4结果与预览结果分开，不能混样。

作为员工，我要把一笔或多笔费用存成草稿，按事由找到这张单，查看明细并继续编辑。

### 业务规则

- 草稿事由为 1～50 字，包含 1～20 条明细。每条明细填写报销类型、金额和费用发生日期，说明可留空，最多 100 字。
- 金额为人民币，单条 0.01～50,000.00 元，最多两位小数。后端按明细计算总额，金额以整数分存储和计算。
- 保存时按北京时间算自然日。从当天向前推 90 天到当天，两端都可选。费用日期按纯日期存储，创建时间等时间点存带时区的时间戳。
- 新明细和换类型的明细只能使用已启用的类型。原明细可以保留后来停用的类型，详情和编辑回显当前名称及停用状态。类型按稳定 ID 关联。
- 草稿由申请人本人读取和编辑。本周用服务端提供的固定虚构身份跑通本地开发和测试。申请人、总额和状态由后端确定，状态为草稿。业务单号在 W05 首次提交时生成。 [PRD 第 2～4 节](../PRD.md#2-角色) · [ADR 0001](../adr/0001-报销类型停用而不删除.md)

### 数据模型与迁移

一张 `expense_reports` 单据对应多条 `expense_report_items` 明细。两表主键由应用生成 UUIDv7，沿用报销类型的发号方式。下表字段均为 `NOT NULL`。

| 表 | 字段 | 类型与约束 |
|---|---|---|
| `expense_reports` | `id` | `uuid` 主键。 |
| `expense_reports` | `applicant_id` | `uuid`。W02 存服务端提供的虚构申请人。W03 的迁移先把已有演示 ID 关联到虚构员工，再加员工外键。 |
| `expense_reports` | `reason` | `varchar(50)`，数据库检查非空字符串。API 去首尾空白后校验 1～50 字。 |
| `expense_reports` | `status` | `varchar(32)`，W02 默认并约束为 `draft`。W05 通过新迁移扩展取值并加入业务单号。 |
| `expense_reports` | `total_cents` | `integer`，范围 1～100,000,000。每次保存由 Service 从本次明细求和并和明细一起写入。 |
| `expense_reports` | `created_at`、`updated_at` | `timestamptz`，由服务端维护。编辑成功更新 `updated_at`，包括只改明细的情况。 |
| `expense_report_items` | `id` | `uuid` 主键。保留和修改的行沿用原 ID，供 W07 的发票附件关联。 |
| `expense_report_items` | `report_id` | `uuid` 外键，指向单据。单据与明细的父子关系用 `ON DELETE CASCADE`，日后整单删除的资格由 Service 检查。 |
| `expense_report_items` | `expense_type_id` | `uuid` 外键，指向 `expense_types.id`，`ON DELETE RESTRICT`。类型名称和启停状态随详情查询读取。 |
| `expense_report_items` | `amount_cents` | `integer`，范围 1～5,000,000。 |
| `expense_report_items` | `incurred_on` | `date`。接口使用 `YYYY-MM-DD`，按北京时间校验。 |
| `expense_report_items` | `description` | `varchar(100)`，默认空字符串。 |
| `expense_report_items` | `position` | `smallint`，范围 1～20。保存时按本次提交的明细顺序赋值，读取按位置及 ID 排序。 |

给主键、外键和检查约束显式命名。单据列表索引使用 `applicant_id, status, created_at DESC, id DESC`，明细索引用 `report_id, position`。明细条数和总额等跨行规则由 Service 在事务里保证。S2 新增 migration，先验 W01 库升级，再验回滚及重跑，继续使用 `synchronize: false`。 [PostgreSQL 约束](https://www.postgresql.org/docs/18/ddl-constraints.html) · [日期类型](https://www.postgresql.org/docs/18/datatype-datetime.html)

### 身份与接口契约

`/api/v1` 下沿用 Controller → Service → Repository 的职责。Controller 从服务端申请人解析入口取得 ID，Service 将申请人和 `draft` 加进列表、详情及更新的数据库条件。开发脚本显式设置 `NODE_ENV=development`，此时本机 API 使用固定虚构身份。测试由服务端注入虚构身份。其他环境在 W03 认证接入前对这些操作返回 401。请求体、查询串和自定义请求头均不能指定申请人。W03 用认证后的当前用户替换解析入口。

| 方法和路径 | 输入 | 成功时的 `data` |
|---|---|---|
| `POST /expense-reports` | `reason`、`items`，新增行均由服务端分配 ID。 | 201，草稿详情。 |
| `GET /expense-reports` | `page` 默认 1，`pageSize` 默认 10、范围 1～50，`keyword` 可选。 | 200，`{ items, page, pageSize, total }`，`total` 是筛选后的总条数。 |
| `GET /expense-reports/:id` | 路径参数 `id` 经过 `ParseUUIDPipe`。 | 200，草稿详情。 |
| `PATCH /expense-reports/:id` | 路径参数 `id` 经过 `ParseUUIDPipe`。提交 `reason` 和完整 `items`，原有行带 `id`，新增行省略 `id`。 | 200，保存后的草稿详情。 |

- 请求明细除编辑时可用的 `id` 外，接受 `expenseTypeId`、`amountCents`、`incurredOn` 和可选的 `description`。金额是 JSON 整数分，例如 10 分传 `10`。申请人、状态、总额和时间均为服务端管理字段。
- 列表行返回 `id`、`reason`、`status`、`totalCents`、`createdAt` 和 `updatedAt`。详情再返回 `items`，每行有 `id`、`expenseType`（`id`、`name`、`enabled`）、`amountCents`、`incurredOn`、`description`。时间点用 ISO 8601 UTC 字符串，日期原样用 `YYYY-MM-DD`。
- 列表按创建时间和 ID 倒序。`keyword` 去首尾空白，限 50 字，空串等同省略。通过参数绑定按字面内容做不区分大小写的事由匹配，转义 SQL 通配符。行查询与计数共用筛选条件，页码超出结果范围返回空列表和总条数。页码和页大小须为正整数，校验计算出的分页偏移也在安全整数范围内。
- 详情用一次关联查询读取单据、明细及当前类型。合法 UUID 对应的单据不存在、属于其他申请人或状态不符合时，统一返回 404 `EXPENSE_REPORT_NOT_FOUND`。

### 校验与统一响应

- Web 从元的小数字符串拆出整数分，转换前校验小数位数，金额显示补足两位。Zod 在 API 边界拒绝未知字段，并校验类型、金额范围、事由和说明长度、明细条数、日期格式及分页参数。文本长度按 Unicode 码点计数。事由去首尾空白，说明可留空且默认 `''`。
- 新建和编辑共用 Service 的业务校验。每次保存取一次服务端当前时间，按 `Asia/Shanghai` 取当天。先判断费用日期是否存在于日历中，再校验是否落在当天前 90 天到当天的闭区间内。Service 计算总额，数据库用字段范围与外键兜住单行数据。
- 服务端在解析请求 JSON 前生成 `requestId`，成功和错误都用它填 `X-Request-Id` 及 JSON 的 `requestId`。在 `configureApp` 接入，使实际启动和测试复用。成功为 `{ data, requestId }`，错误为 `{ code, message, requestId, fieldErrors? }`。每条字段错误有 `path` 和 `message`，路径段使用字段名及从 0 开始的数组下标。`['items', 1, 'amountCents']` 指向第二条明细的金额。组装错误时保留原 HTTP 状态。

| HTTP | 错误码 | 场景 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 路径、查询或请求体非法。类型不存在、类型停用但用于新行或换类型，以及明细 ID 重复或不属于本单据，都定位到提交的字段。无法解析的 JSON 同样返回 400。 |
| 401 | `UNAUTHENTICATED` | 服务端没有可用于草稿操作的申请人身份。 |
| 404 | `EXPENSE_REPORT_NOT_FOUND`、`EXPENSE_TYPE_NOT_FOUND` 或 `NOT_FOUND` | 按当前数据范围找不到对应单据、报销类型或路由。 |
| 409 | `EXPENSE_TYPE_NAME_TAKEN` | 新增或改名时命中类型查重，或者 PostgreSQL 报 `23505` 且约束为 `uq_expense_types_name`。 |
| 500 | `INTERNAL_ERROR` | 未知异常，外部只收到通用提示和请求 ID。 |

S3 同步切换健康检查和类型接口的响应、Web 公共 HTTP 层及测试。健康检查以 `{ status: 'ok' }` 为 `data`，类型接口继续返回列表或单条记录，保留新增 201、查询与修改和启停 200。HTTP 层解包成功数据，`ApiError` 保留状态、业务码、请求 ID 和字段错误。超时、取消、网络错误和 204 空响应沿用公共层的处理。S4 为类型新增和编辑补严格校验，新增必须给 `name`，编辑可只传 `description`。写入名称时去首尾空白，按相同规则检查启用和停用的已有类型名称，排除当前行。W01 历史名称按原样读取。 [Nest 异常过滤器](https://docs.nestjs.com/exception-filters) · [PostgreSQL 错误码](https://www.postgresql.org/docs/18/errcodes-appendix.html)

### 保存事务、类型停用与重复请求

1. 新建先校验请求结构，再进入 TypeORM 事务。编辑在事务内按单据 ID、申请人和状态锁定单据行（`FOR UPDATE`），然后读取本单据当前的明细。校验原行 ID 都属于该单据且各出现一次。提交中省略的原行会从草稿移除。
2. 类型模块提供可在同一事务下按 ID 批量读取的接口。新行和修改类型的行要求类型存在且启用，检查期间对对应类型行加共享锁（`FOR SHARE`）。保存和停用谁先拿到锁，谁先完成该项变更。保留原类型的行可继续引用已停用的类型，查询仍返回它的当前名称及启停状态。
3. 更新单据及总额，处理移除、保留和新增的明细，再组装详情。事务内的读写都使用当前事务的 `EntityManager`，成功响应只在提交后发出。任一步数据库写失败，单据和明细一同回滚。

两次编辑同一张单会串行写入。后一次基于前一次提交后的明细检查 ID，引用已移除的行会报字段错误，其余情况下以最后成功的保存为准。W05 用版本号识别用户拿着旧表单保存的冲突。重复发送新建请求可能产生两张草稿，W06 通过幂等键处理。重复编辑按完整集合应用，明细条数不会累加，新行的 ID 可能重新生成。 [TypeORM 事务](https://typeorm.io/docs/transactions/) · [PostgreSQL 行级锁](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)

- **完成标准** 设计能解释 A1～A9 的关键路径，评审意见中没有必须改。
- **概念与 L1** 一对多关系和事务分别约束数据怎么关联、哪些写入一起提交。先看 TypeORM 的关系和事务章节。 [一对多关系](https://typeorm.io/docs/relations/many-to-one-one-to-many-relations/) · [事务](https://typeorm.io/docs/transactions/)

### S2 单据、明细与专用测试库（约 1.5 小时）

- 作者按评审后的设计补实体和 migration，建立 PostgreSQL 专用测试库。记录库名、测试命令与清理边界。测试进程从显式配置取得连接信息，配置缺失或指向其他库时在连接前报错。测试数据与迁移验证都在专用库进行。
- **完成标准** 在专用库用已有迁移建出 W01 结构后再升级，检查外键和关键约束。新增迁移可回滚再重跑。健康检查测试可脱离数据库运行。
- **概念与 L1** 外键保护明细引用，数据库约束给每次写入兜底。查 PostgreSQL 约束和 Nest 集成测试的应用初始化。 [PostgreSQL 约束](https://www.postgresql.org/docs/18/ddl-constraints.html) · [Nest 测试](https://docs.nestjs.com/fundamentals/testing)

### S3 统一 API 响应（约 1.5 小时）

- 作者接入统一成功响应和全局异常过滤器，沿用 `configureApp` 让启动和测试共用配置。助手同步调整公共 HTTP 层，让业务 API 继续把业务数据或 `ApiError` 交给页面。
- **完成标准** 健康检查和报销类型接口的成功、404 和错误响应符合新约定，原有 HTTP 状态含义保留。Web 健康状态、报销类型调用和请求契约测试通过。覆盖 A7 的公共契约。
- **概念与 L1** HTTP 状态给调用方判断请求结果，业务错误码区分同一状态下的业务失败。查 Nest 如何处理内置异常和未知异常。 [Nest 异常过滤器](https://docs.nestjs.com/exception-filters)

### S4 Zod 校验与报销类型回归（约 1.5 小时）

- 作者建立可复用的 Zod 请求校验入口，先覆盖 W01 类型新增和改名。检查必填、首尾空格、长度、未知字段和重名，把并发触发的名称唯一约束错误归到同一个重名业务错误。
- **完成标准** 在专用库用 API 验证不合法字段返回 400、重复名称返回 409。集成测试覆盖 Service 查到重名和写入撞到数据库唯一约束两条路径，确认并发时只保留一条记录。覆盖 A7 的类型边界。
- **概念与 L1** TypeScript 类型在编译时检查，API 收到的 JSON 需要运行时校验。查 Nest 管道与 Zod 对象的严格模式。 [Nest 管道](https://docs.nestjs.com/pipes) · [Zod 严格对象](https://zod.dev/api#zstrictobject)

### S5 新建草稿（约 2 小时）

- 作者用 Zod 校验草稿请求，Service 校验类型与费用日期、计算整数分总额。用同一个事务保存单据与全部明细。为金额、明细条数和日期边界增加单元测试，日期测试固定时钟并覆盖北京时间换日。
- **完成标准** 通过 API 建出两行草稿并查到正确总额。专用库测试在部分写入后触发失败，确认新建整体回滚。覆盖 A1、A4、A6 的新建部分。
- **概念与 L1** 事务内的 Repository 要和事务使用同一连接。查 TypeORM 的事务上下文。 [TypeORM 事务](https://typeorm.io/docs/transactions/)

### S6 草稿详情与编辑（约 2 小时）

- 作者实现详情和编辑。读取按申请人范围定位单据，显示关联类型当前名称。编辑沿用新建校验与金额计算规则，处理原行保留停用类型的情形，在一个事务内完成单据和明细的变化。
- **完成标准** API 验证详情、编辑、跨申请人访问和停用类型边界。编辑测试先保存一张合法草稿，在一部分更新写入后触发失败，再从库中读回完整原值。覆盖 A2、A5 与 A6 的编辑部分。
- **概念与 L1** 明细 ID 标识单据里的原有行。对照 PRD 和 ADR 思考怎样区分保留原行与新填一行。 [业务规则](../PRD.md#4-业务规则) · [ADR 0001](../adr/0001-报销类型停用而不删除.md)

### S7 草稿列表分页与筛选（约 1 小时）

- 作者实现按申请人、草稿状态和事由关键词查询，统一校验分页参数。列表和总条数使用同一筛选条件，排序能确定同一创建时间内的记录顺序。
- **完成标准** 在专用测试库建超过一页的草稿和其他申请人的记录。确认分页、筛选、总数、排序和范围符合 A3、A4、A5 的 API 要求。
- **概念与 L1** 分页决定取哪一段数据，稳定排序决定每条数据在列表中的位置。查 TypeORM 查询选项的 `order`、`skip` 和 `take`。 [TypeORM 查询选项](https://typeorm.io/docs/working-with-entity-manager/find-options/)

## 一、用户场景与范围

用户修改误填的虚构流水、确认删除不需要的记录，并按上海自然月核对收入/支出/净额及分类明细。

必做：流水PATCH/DELETE、月报API/页面、分类下钻、软删更新、创建首次响应重放、主流程E2E。暂不做图表、导出、乐观锁、预算、多币种。

历史流水显示分类最新名称；已归档分类标注归档。同名新分类与旧分类按ID分列，不能按名称合并。该阶段设计采用总技术方案的明确规则。

## 二、需求与验收编号

| 编号 | 产品行为 |
|---|---|
| M3-R01 | PATCH仅允许direction/categoryId/amountMinor/occurredAt/note；currency/id/userId等拒绝；校验最终合并对象。 |
| M3-R02 | 编辑自己的未删流水200；他人/不存在/已删404；选定分类须本人、方向匹配、未归档。 |
| M3-R03 | DELETE本人流水软删204，重复本人删除仍204；他人/不存在404；不得泄露他人资源。 |
| M3-R04 | monthly返回month/timeZone/hasEntries、分字符串incomeTotalMinor/expenseTotalMinor/netMinor、分类金额/条数。 |
| M3-R05 | 无记录与净额为0区分；已删不统计；跨年/闰年/上海午夜边界正确。 |
| M3-R06 | 同键重放首次201/Location/body，后续编辑或软删不重建、不替换首次快照；冲突体409。 |
| M3-R07 | Web删除二次确认，成功后列表/月报同时更新；修改后分类/月份相关缓存失效。 |

## 三、接口与口径

| 接口/字段 | 规则 |
|---|---|
| PATCH /api/v1/entries/{id} | UUID、Cookie、Origin、CSRF；部分字段覆盖不累加；本期最后一次有效提交生效。 |
| DELETE /api/v1/entries/{id} | 204无body；拥有权以数据库为准；重复删除本人记录成功。 |
| GET /api/v1/reports/monthly?month=YYYY-MM | month必需；支持2000～2100；400非法参数，401未登录，503DB不可用。 |
| 分类聚合 | 按categoryId+direction分组；含name/archived、amountMinor、entryCount；净额=收入-支出，可以负数。 |

## 四、交互与历史编辑规则

编辑归档分类的历史流水时仍可查看原分类；提交编辑要重新选择有效匹配分类，提示原因而非静默改分类。金额/币种不能隐式改变。

发生日期变化可能将记录移到另一月份；Web失效旧月和新月列表/报表，再重新请求，不能靠当前列表本地减金额冒充统计。

无记录提示“该月无记录”；有收支相抵显示“净额0”且保留条数；非AI页面不显示“AI生成”。

客户端幂等操作结果未知仍沿用原键；成功后的“再记一笔”才用新键。PATCH/DELETE可按定义安全重试，但最后提交覆盖的编辑语义须界面明确。

## 五、出门条件

固定虚构数据手工SQL与API月报逐字段一致；分类之和等于总额，记录数正确，已删排除。

修改/删除后重放原创建键不会新建记录；故障回滚不残留占位幂等行。

完整登录→分类→创建→月报→修改/删除→退出E2E；A不能查看/改/删B；手机与键盘操作可用。

## 技术设计（S5：作者写了两版初稿，应作者要求由助手按评审意见给出最终方案）

### 要设计的是什么

报销类型是管理员维护的一份字典，比如差旅、交通、餐饮、办公用品。员工在 W2 填报销明细时从下拉框里选一个，财务按它统计。它没有金额、时间、付款方式，这些属于 W2 的报销明细。

### 数据：表 `expense_types`

| 字段 | 类型 | 必填 | 约束与默认值 | 说明 |
|---|---|---|---|---|
| `id` | `uuid` | 是 | 主键 | UUIDv7，由应用用 Node 的 `crypto.randomUUIDv7()` 生成 |
| `name` | `varchar(20)` | 是 | 唯一约束 `uq_expense_types_name` | 名称，去掉首尾空格后 1～20 个字；`varchar(n)` 按字符计数，一个汉字算 1 |
| `description` | `varchar(100)` | 是 | 默认 `''` | 说明，可以不填，不填时存空字符串 |
| `enabled` | `boolean` | 是 | 默认 `true` | `true` 启用，`false` 停用 |
| `created_at` | `timestamptz` | 是 | 默认 `now()` | 创建时间，列表按它倒序 |
| `updated_at` | `timestamptz` | 是 | 默认 `now()` | 最后修改时间，每次修改时更新 |

决定和理由：

- 主键用 UUIDv7，不用名称、流水号，也不用自增整数：
  - 主键必须永远不变，而业务字段会变（PRD 允许改名），所以主键用没有业务含义的编号；
  - 自增整数能被猜（改地址里的数字就能试探下一条），还会暴露数据量；
  - 完全随机的 UUID（v4）写入时会打乱索引顺序，数据多了变慢；UUIDv7 前半段是时间，按生成顺序递增，没有这个问题；
  - 由应用生成：S6 的内存版就能用，S8 换成数据库后这部分不用改。手工在 psql 里插数据时，可以用 PostgreSQL 18 自带的 `uuidv7()`。
- 停用用布尔字段 `enabled`：PRD 只有启用、停用两种状态，布尔最简单，查"启用的类型"也最直接；谁、什么时候停用的，由 W6 的操作日志记录，不放进这张表。
- 不能删除，只能停用：W2 起报销明细会引用报销类型，删掉后历史单据就找不到它的类型了（S9 的 ADR 0001 展开写）。
- 说明不填时存空字符串而不是 NULL：避免"空"有两种写法，前后端都不用再判断 null。
- 时间点用 `timestamptz`：存的是绝对时刻，不会因为服务器时区不同而变。TypeORM 默认建成不带时区的 `timestamp`，S8 要显式写明。
- 表名、列名用小写加下划线，接口和代码里用驼峰（`createdAt`）；约束显式命名，以后的 migration 要改它时能直接写出名字。

### 名称的规则

- 首尾空格不算：保存前去掉首尾空格，"差旅 "和"差旅"是同一个名称。
- 其余按严格相等比较：英文大小写不同算两个名称。报销类型基本是中文，先不处理；以后需要时，把唯一约束改成按 `lower(name)` 建的唯一索引。
- 已停用的也不能重名：唯一约束覆盖所有行，不区分启用、停用。
- 改名时只和其他记录比较，不和自己比：编辑弹窗会把名称和说明一起提交，只改了说明、名称没变时不能报重名。

### 接口（前缀 `/api/v1`）

返回的报销类型对象是 `{ id, name, description, enabled, createdAt, updatedAt }`，时间是 ISO 8601 字符串。本周直接返回对象和数组，W2 统一响应格式。

| 方法 | 路径 | 请求体 | 成功 | 失败 |
|---|---|---|---|---|
| GET | `/expense-types` | 无 | 200，数组 | — |
| POST | `/expense-types` | `{ name, description? }` | 201，新建的对象 | 400 参数不合法；409 名称已存在 |
| PATCH | `/expense-types/{id}` | `{ name?, description? }` | 200，修改后的对象 | 400；404 不存在；409 名称已存在 |
| POST | `/expense-types/{id}/disable` | 无 | 200，修改后的对象 | 404 不存在 |
| POST | `/expense-types/{id}/enable` | 无 | 200，修改后的对象 | 404 不存在 |

- 不提供 DELETE：PRD 规定不能删除。也不提供查单个的接口：编辑弹窗直接用列表里的数据，用不上。
- 启用、停用做成单独的动作接口，不通过 PATCH 改 `enabled`：
  - 停用是一个业务动作，W4 可以给它单独授权，W6 可以按动作记操作日志；
  - 和 W5 报销单的提交、审批、驳回（也都是动作接口）保持一致；
  - 已经停用的再停用一次，直接返回 200，不报错（幂等），连点两次也没问题。
- PATCH 只改传了的字段。后端只取 `name`、`description` 两个字段，不能把请求体整个合并进数据：否则客户端顺手传一个 `enabled`、`id` 或 `createdAt`，就能改掉不该改的字段（批量赋值漏洞）。
- 列表排序：`created_at DESC, id DESC`。只按创建时间排，同一时刻创建的两条顺序不固定；加上 `id` 兜底，顺序才稳定。

### 规则在哪一层检查

| 规则 | 前端 | 后端 | 数据库 | 本周做到 |
|---|---|---|---|---|
| 名称必填，去首尾空格后 1～20 字 | 表单校验，提交前去空格 | W2 用 Zod 校验并去空格 | `NOT NULL`、`varchar(20)`；W2 加检查约束：不能为空白、已去首尾空格 | 前端；数据库的非空和长度 |
| 名称不重名（包括已停用的） | 不做：前端看不到别人同时提交的数据 | 先查重，重名返回 409 | 唯一约束兜底 | 后端查重和唯一约束 |
| 说明最多 100 字 | 表单校验 | W2 用 Zod 校验 | `varchar(100)` | 前端和数据库 |
| 新建默认启用；客户端不能改 `id`、`enabled`、时间 | — | 只取 `name`、`description` | `enabled` 默认 `true` | 后端和数据库 |
| 不能删除 | 没有删除按钮 | 没有 DELETE 接口 | W2 起报销明细的外键阻止删除被引用的类型 | 前端和后端 |
| 停用的类型不能用于新明细 | 下拉框只列启用的 | W2 新建明细时检查 | — | W2 |

前端校验是为了体验，后端校验是为了正确（别人可以绕过页面直接调接口），数据库约束是最后一道防线。

### 并发与重复请求

- 同时新增同名类型：后端"先查再插"挡不住，两个请求可能同时查到"不存在"。由数据库唯一约束兜底，第二条插入失败；本周这种情况返回 500，W2 把唯一约束的错误也转成 409。
- 两个管理员同时修改同一个类型：后保存的覆盖先保存的。这是有意的决定：管理员少、改动不频繁、改错了影响小。
  - 不用"加锁"解决：数据库的锁只在一个事务里持有，通常几毫秒；两个人各自打开编辑弹窗、隔几分钟再保存，数据库锁挡不住。
  - 真要防，用乐观锁：表里加版本号，保存时带上读到的版本号，版本对不上就拒绝（409），让后保存的人刷新后重来。W5 的报销单审批会用到。
- 连点两次保存：前端在请求期间禁用确认按钮；就算发出了两次新增，第二次也会因为重名失败。启用、停用接口是幂等的，连点没有影响。

### 前端

表格四列：名称、说明（为空显示「—」）、状态、操作；右上角「新增类型」按钮。新增和编辑共用一个弹窗，字段是名称和说明。

| 情况 | 页面显示 |
|---|---|
| 列表加载中 | 表格显示加载状态 |
| 一条数据都没有 | 表格显示「暂无数据」，「新增类型」按钮照常可用 |
| 列表加载失败 | 表格上方显示错误提示和「重试」按钮 |
| 点了保存、结果还没回来 | 确认按钮显示加载中，不能再点 |
| 保存成功 | 关闭弹窗，提示「已保存」，列表重新获取 |
| 保存失败：名称重复（409） | 弹窗不关，名称输入框下显示「名称已存在」 |
| 保存失败：其他错误（包括本周并发重名的 500） | 弹窗不关，保留已填内容，提示「保存失败，请稍后重试」 |
| 停用 | 先确认：「停用后不能再用于新的报销单，已有单据不受影响。确定停用？」；启用没有副作用，直接执行 |
| 停用、启用进行中 | 这一行的按钮显示加载中 |

- 概念：浏览器默认不让页面读取"不同源"（协议、域名、端口任一不同）接口的响应，这叫同源策略。开发时页面在 5173、API 在 3000，属于不同源。解法有两种：API 返回 CORS 响应头，声明允许这个来源；或者让 Vite 把请求转发过去，浏览器只看到同源请求。本项目开发时用 Vite 转发，W8 起用 Nginx 转发，所以不开 CORS；这也是 W10 网关的雏形。

  - 代理目标写 `http://127.0.0.1:3000`，不要写 `localhost`：本机的 `localhost` 可能先解析成 IPv6 的 `::1`（S2 验证时 Vite 就监听在 `[::1]:5173`），而 API 只监听 IPv4 的 `127.0.0.1`，代理会连不上。

  - API 停掉时，Vite 代理返回 502，Vite 的终端里会打印 `http proxy error`，这是正常现象。`fetch` 只在网络断开时才进 catch，502 要靠 `response.ok` 判断。

### S6 报销类型 v0：内存版接口（约 2 小时）

- 做什么：用 Nest CLI 生成报销类型的 module、controller、service；数据先存在 service 里的数组中；实现 S5 设计的接口；用 curl 或 `.http` 文件把每个接口调一遍。
- 完成标准：每个接口的行为和状态码符合设计；重启 API 后数据消失（故意的，S8 解决）。
- 概念：Controller 负责接收 HTTP 请求、返回响应；Service 负责业务逻辑；Module 把它们组装起来。Controller 不自己 `new` Service，而是在构造函数里声明"我需要它"，由 Nest 创建好再传进来，这叫依赖注入。这样同一个 Service 可以在多处共用，测试时也能换成替身；如果每个类都自己 `new` 依赖，换一个实现就要改一大片代码。
- 注意：
  - `nest g` 生成的文件，以及它往 `app.module.ts` 里加的导入，用的都是相对路径，生成后改成 `@/`（多出来的分号会在提交时被 Prettier 去掉）。
  - 按「技术设计」实现：`id` 用 Node 自带的 `crypto.randomUUIDv7()` 生成；新增和改名时先查重，重名返回 409（改名时排除这条记录自己）；找不到 id 返回 404。Nest 的 `ConflictException`、`NotFoundException` 会返回这两个状态码。
  - PATCH 只取 `name`、`description`，不要把请求体整个合并进数据。

### S8 换成 PostgreSQL（约 2.5 小时）

- 做什么：
  1. 用 `@nestjs/config` 从 `.env` 读取 `DATABASE_URL`，启动时校验它存在；提交 `.env.example`，不提交 `.env`。
  2. 接入 TypeORM，`synchronize` 必须为 `false`；写报销类型的 Entity。
  3. 配置 TypeORM CLI，生成第一个 migration，先读懂生成的 SQL，再执行到 `expense_dev`。
  4. Service 从数组改为 Repository；后端查重保留，数据库唯一约束兜底。
- 完成标准：验收标准 6～8 通过；在 `psql` 里看到的表结构和约束与「技术设计」一致；再执行一次 migration 不会重复建表。
- 概念：Entity 是"表在代码里的样子"，migration 是"改表的脚本"，两者不是一回事。`synchronize: true` 会在启动时按 Entity 自动改表，开发时省事，但可能悄悄删列、丢数据，而且其他环境不知道你改了什么。migration 把每次改动写成带版本号的脚本，提交到 git，每个环境按顺序执行，谁都能复现。
- 注意：
  - 仓库根目录还留着旧项目的 `.env`（旧库的连接串和会话密钥），先删掉，再按你的 `.env.example` 新建，免得连到旧库。`.env` 放根目录还是 `apps/api/`，先想好再动手。
  - Nest 12 脚手架是 ESM（`"type": "module"`），TypeORM CLI 直接加载 `.ts` 配置容易出错；可以先构建，再让 CLI 加载 `dist` 里编译好的数据源文件。这一处卡住超过 15 分钟就找我，它属于工具链问题。
  - 创建时间、更新时间用 `@CreateDateColumn`、`@UpdateDateColumn`，并显式写 `type: 'timestamptz'`：TypeORM 默认建成不带时区的 `timestamp`（已查 TypeORM 1.1.2 源码）。
  - 主键值和 S6 一样由应用生成，实体里用普通的主键列；不要用 `@PrimaryGeneratedColumn('uuid')`，它让数据库生成随机的 UUIDv4。
  - 唯一约束按设计显式命名为 `uq_expense_types_name`。
- L1：[Nest Database](https://docs.nestjs.com/techniques/database)、[Nest Configuration](https://docs.nestjs.com/techniques/configuration)、[TypeORM Entities](https://typeorm.io/docs/entity/entities)、[Migrations 原理](https://typeorm.io/docs/migrations/why)、[Migrations 配置](https://typeorm.io/docs/migrations/setup)。

## 请求路线图（S4 应作者要求由助手画，S8 接上数据库后补全）

页面打开时请求健康检查接口，一次请求经过这些站：

```text
① 浏览器：页面在 http://localhost:5173
   ApiStatus 组件调用 fetchHealth()，发出 GET /api/v1/health
   只写路径，所以请求发给页面自己所在的 5173：同源请求，浏览器不拦截
        │
        ▼
② Vite 开发服务器（localhost:5173）
   server.proxy 看到路径以 /api 开头，原样转发给 http://127.0.0.1:3000
   （上线后由 Nginx 做这一步，W8、W10）
        │
        ▼
③ Nest（127.0.0.1:3000，底层是 Express）
   全局前缀 api/v1 + @Controller('health') + @Get()，拼出 GET /api/v1/health，匹配到 HealthController.getHealth()
        │
        ▼
④ HealthController.getHealth() 返回 { status: 'ok' }
   Nest 把返回的对象转成 JSON：状态码 200，Content-Type: application/json
        │
        ▼
⑤ 原路返回：Nest → Vite → 浏览器
   fetchHealth() 看到 response.ok，ApiStatus 显示「API 已连接」
```

API 停掉时，第 ② 站连不上 3000，Vite 自己返回 502，并在终端打印 `http proxy error`；fetchHealth() 看到 `response.ok` 为假就抛错，页面显示「API 不可用」。

S8 接上数据库后，报销类型接口会在第 ④ 站后面多出 Service → Repository → PostgreSQL 这几站。

## 需求

用户故事：作为系统管理员，我要维护报销类型（例如差旅、交通、餐饮、办公用品），这样员工填报销单时可以选择类型，财务也能按类型统计。

页面草图：

```text
┌ 星河报销 ─────────────────────────────── API 已连接 ┐
│ 侧边栏          │ 报销类型                [ 新增类型 ] │
│ · 报销类型      │ ┌──────┬────────────┬──────┬──────────┐ │
│                 │ │ 名称 │ 说明       │ 状态 │ 操作     │ │
│                 │ │ 差旅 │ 出差交通住宿│ 启用 │ 编辑 停用│ │
│                 │ │ 招待 │            │ 停用 │ 编辑 启用│ │
│                 │ └──────┴────────────┴──────┴──────────┘ │
└─────────────────┴────────────────────────────────────────┘
「新增类型」和「编辑」打开弹窗表单（名称、说明），保存后列表刷新。
```

业务规则（来自 [PRD](../PRD.md) 第 4 节）：

- 名称必填，1～20 个字（首尾空格不算），不能和已有类型重名，包括已停用的。
- 说明选填，最多 100 字。
- 新建的类型默认启用；类型不能删除，只能停用和重新启用。
- 列表按创建时间倒序。

验收标准（在浏览器里逐条走一遍）：

1. 打开「报销类型」页面看到列表；没有数据时显示空状态。
2. 新增"差旅"，弹窗关闭后列表立刻出现这一条，状态为启用。
3. 编辑"差旅"的说明，保存后列表显示新说明。
4. 停用"差旅"前有二次确认，停用后状态变为停用；再启用，恢复为启用。
5. 名称为空、超过 20 字，或说明超过 100 字时，表单不能提交，并提示原因。
6. 重启 API 进程后刷新页面，数据还在。
7. 在终端用 curl 调用新增接口，返回 201 和新建的数据。
8. 新增或改名成已有类型的名称（包括已停用的），不会出现两条同名记录（本周接口返回 500 也接受，W2 改成清楚的错误提示）。
9. API 停止时，页面顶栏显示"API 不可用"，页面不白屏。

本周故意不做（先亲手遇到问题，后面再解决）：

- 登录和权限：现在谁都能改报销类型（W3、W4）。
- 后端校验和统一错误格式：本周只在前端表单校验。用 curl 传空名称、超长名称、首尾带空格的名称，看看会发生什么，把现象记进复盘（W2）。
- 分页：类型很少，用不上（W2 的报销单列表再做）。
- 自动生成接口类型：本周前端手写类型，体会它和后端对不上的风险（W2）。
- 业务测试：本周只保证现有测试能跑；W2 开始给业务规则写测试，并连真实数据库。

- 注意：
  - 已经在 git 仓库里了，Nest CLI 要跳过它自带的 `git init`；它还会询问是否开启观测性，先不开（W6 再做）。用 `nest new --help` 查参数。

  - 依赖写精确版本，不带 `^`、`~`。
  - pnpm 12 默认有一天的发布冷却期（`minimumReleaseAge`）：发布不到一天的版本不装。供应链投毒（攻击者拿到某个包的发布权限，发一个带恶意代码的新版本）通常几小时内就会被发现并下架，晚一天装能躲开大部分这类攻击。如果你手写了太新的版本号，pnpm 会在 `pnpm-workspace.yaml` 里自动加一段 `minimumReleaseAgeExclude` 放行它。看到这段就删掉，改用 `pnpm add -E <包名>`（不写版本号）重装这些包：pnpm 会选冷却期外的最新版本，也不会再加例外。例如 Nest 在 10-27 一天内连发了 12.3.0～12.3.2，10-28 这样装得到的是 12.2.0。
  - 这套组合（Node 26.12.1、pnpm 12.15.0、两端 TypeScript 6.0.3）助手已在临时目录验证过：两端构建、lint 和 Nest 自带的测试都能通过，版本组合本身没有问题。
- L1：[pnpm workspace](https://pnpm.io/workspaces)、[pnpm 供应链安全](https://pnpm.io/supply-chain-security)、[Nest First steps](https://docs.nestjs.com/first-steps)；pnpm 的 `--filter`、`-r --parallel` 和 `saveExact` 设置。

### S4 第一次前后端连通 + Review（约 2 小时）

- 做什么：API 加统一前缀 `/api/v1`，提供 `GET /api/v1/health` 返回 `{ "status": "ok" }`；Vite 开发服务器把 `/api` 转发给 API；首页用 Ant Design 布局（顶栏 + 侧边栏 + 内容区），顶栏显示 API 连接状态；在本文件「请求路线图」一节画出这次请求经过的每一站。做完告诉我，我按 [Review 清单](templates.md#3-code-review-清单) review S2～S4 的提交，你改到没有"必须改"。
- 完成标准：页面显示"API 已连接"；停掉 API 再刷新，显示"API 不可用"；浏览器开发者工具的 Network 面板里，请求发往 5173 端口而不是 3000；Review 没有"必须改"。
- 概念：浏览器默认不让页面读取"不同源"（协议、域名、端口任一不同）接口的响应，这叫同源策略。开发时页面在 5173、API 在 3000，属于不同源。解法有两种：API 返回 CORS 响应头，声明允许这个来源；或者让 Vite 把请求转发过去，浏览器只看到同源请求。本项目开发时用 Vite 转发，W8 起用 Nginx 转发，所以不开 CORS；这也是 W10 网关的雏形。
- 注意：
  - 让 API 只监听 `127.0.0.1`，开发机上的服务不要暴露给局域网。
  - 代理目标写 `http://127.0.0.1:3000`，不要写 `localhost`：本机的 `localhost` 可能先解析成 IPv6 的 `::1`（S2 验证时 Vite 就监听在 `[::1]:5173`），而 API 只监听 IPv4 的 `127.0.0.1`，代理会连不上。
  - Ant Design 默认是英文（例如空表格显示 No data），用 `ConfigProvider` 配成中文。
- L1：[Vite server.proxy](https://vite.dev/config/server-options)、[MDN CORS](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Guides/CORS)；Nest 的 `setGlobalPrefix`。

### S6 报销类型 v0：内存版接口（约 2 小时）

- 做什么：用 Nest CLI 生成报销类型的 module、controller、service；数据先存在 service 里的数组中；实现 S5 设计的接口；用 curl 或 `.http` 文件把每个接口调一遍。
- 完成标准：每个接口的行为和状态码符合设计；重启 API 后数据消失（故意的，S8 解决）。
- 概念：Controller 负责接收 HTTP 请求、返回响应；Service 负责业务逻辑；Module 把它们组装起来。Controller 不自己 `new` Service，而是在构造函数里声明"我需要它"，由 Nest 创建好再传进来，这叫依赖注入。这样同一个 Service 可以在多处共用，测试时也能换成替身；如果每个类都自己 `new` 依赖，换一个实现就要改一大片代码。
- L1：[Controllers](https://docs.nestjs.com/controllers)、[Providers](https://docs.nestjs.com/providers)、[Modules](https://docs.nestjs.com/modules)。`nest g resource` 会多生成暂时用不到的文件，想想用不用它。

### S8 换成 PostgreSQL（约 2.5 小时）

- 做什么：
  1. 用 `@nestjs/config` 从 `.env` 读取 `DATABASE_URL`，启动时校验它存在；提交 `.env.example`，不提交 `.env`。
  2. 接入 TypeORM，`synchronize` 必须为 `false`；写报销类型的 Entity。
  3. 配置 TypeORM CLI，生成第一个 migration，先读懂生成的 SQL，再执行到 `expense_dev`。
  4. Service 从数组改为 Repository；重名由数据库唯一约束兜底。
- 完成标准：验收标准 6～8 通过；在 `psql` 里看到的表结构和约束与你的设计一致；再执行一次 migration 不会重复建表。
- 概念：Entity 是"表在代码里的样子"，migration 是"改表的脚本"，两者不是一回事。`synchronize: true` 会在启动时按 Entity 自动改表，开发时省事，但可能悄悄删列、丢数据，而且其他环境不知道你改了什么。migration 把每次改动写成带版本号的脚本，提交到 git，每个环境按顺序执行，谁都能复现。
- 注意：
  - 仓库根目录还留着旧项目的 `.env`（旧库的连接串和会话密钥），先删掉，再按你的 `.env.example` 新建，免得连到旧库。`.env` 放根目录还是 `apps/api/`，先想好再动手。
  - Nest 12 脚手架是 ESM（`"type": "module"`），TypeORM CLI 直接加载 `.ts` 配置容易出错；可以先构建，再让 CLI 加载 `dist` 里编译好的数据源文件。这一处卡住超过 15 分钟就找我，它属于工具链问题。
- L1：[Nest Database](https://docs.nestjs.com/techniques/database)、[Nest Configuration](https://docs.nestjs.com/techniques/configuration)、[TypeORM Entities](https://typeorm.io/docs/entity/entities)、[Migrations 原理](https://typeorm.io/docs/migrations/why)、[Migrations 配置](https://typeorm.io/docs/migrations/setup)。

# 星河报销｜13 周全栈学习计划

- 周期：2026-10-28 ～ 2027-01-31，13 周，每周约 15 小时
- 当前：W01 未开始，见 [W01-从零跑通](W01-从零跑通.md)
- 业务需求：[PRD](../PRD.md)；模板与 Review 清单：[templates.md](templates.md)；架构决策：[ADR](../adr/README.md)
- 上一版（个人账本、后端先行）已归档为 tag `v1-backend-first`。可以用 `git show v1-backend-first:<路径>` 对照思路，但不复制其中的代码。

## 一、目标

13 周后得到一个部署上线的企业费用报销系统，并且：

- 前后端每一层都是自己写的，能讲清楚每个设计为什么这样做、不这样做会出什么问题；
- 代码达到下文「企业级清单」的标准，可以作为面试项目；
- 有一份自己作答、经过批改的面试题库，以及项目亮点的讲述稿。

## 二、方法

每周一个迭代，每个迭代交付在浏览器里能用的功能。迭代内拆成不超过 2 小时的小步，每一步都是"页面 + 接口 + 表"的一小片。

每个迭代按公司研发流程走：

1. 需求（助手写）：用户故事、文字版页面草图、业务规则、验收标准，不含代码。
2. 技术设计（作者写，约 20 分钟）：按[模板](templates.md#1-技术设计模板)回答表、接口、规则、并发等问题；评审通过后再写代码。
3. 编码（作者写）：前端、后端、测试、配置都由作者写。先查官方文档，卡住超过 15 分钟再要提示。
4. 自测：在浏览器里逐条走验收标准，跑检查命令。
5. Code Review（助手做）：看分支相对 main 的 diff，按清单给出「必须改 / 建议改 / 可讨论」。
6. 重构（作者改）：改到没有"必须改"。
7. 复盘（作者写，约 15 分钟）：用自己的话写下 3 个核心概念，回答当周的面试题，助手批改。

三级提示，要到哪一级由作者决定：L1 方向（查哪份文档、用哪个概念或 API）→ L2 思路（步骤或伪代码）→ L3 片段（只给卡住那一处的几行代码）。

先跑通，再升级：每周文档写明"本周故意先不做什么"，让作者先亲手遇到问题，后面再升级。例如登录第一版只有短期 token，刷新页面或过期就掉线，下一版再做 refresh token 无感刷新。

测试只测关键处：每个功能测关键业务规则（状态流转、权限、金额）和主流程接口，一般几条到十几条，接口测试连真实数据库。端到端测试放到 W11。

文档保持轻量：总计划一份；每周一份迭代文档，只有当前这周写详细，后面的周只有下表中的一行；重要的技术选择由作者写成一页 ADR。

建议节奏：工作日选 3 个晚上，每次 2 小时，学概念、做小步；周末两天各 4.5 小时，完成竖切、Review 和重构。

## 三、技术栈

| 层 | 选择 |
|---|---|
| 前端 | React 19 + TypeScript + Vite；Ant Design 6；React Router；TanStack Query（服务端数据）；Zustand（登录态与权限）；axios（请求层、无感刷新）；ECharts（W9）；接口类型由 OpenAPI 生成（W2 起） |
| 后端 | NestJS 12（Express 适配器）+ TypeORM + PostgreSQL 18；Zod 校验（W2）；@nestjs/jwt + Argon2id（W3）；Swagger 生成 OpenAPI |
| 工程 | pnpm monorepo（`apps/web`、`apps/api`）；oxlint + Prettier；husky + lint-staged + commitlint；Vitest + Supertest；Playwright（W11）；功能分支 + GitHub PR |

- 版本：Node 26.12.1（26.x 于 2026-10-28 进入 LTS，10-21 发布了修复高危漏洞的安全更新）；TypeScript 两端统一 6.0.3（Nest CLI 依赖 6.0.x，openapi-typescript 还不支持 7.x，而 create-vite 模板默认带 7.x）；依赖写精确版本，安装当天取最新稳定版。
- Linter 用 oxlint：Nest CLI 12 和 create-vite 9 的官方模板默认都用它，沿用默认，不再另配 ESLint。
- 明确不做：微服务、Kubernetes、GraphQL、Kafka/RabbitMQ、第二套 ORM、SSR。面试会问这些概念，放进对应周的面试题，讲清"为什么本项目不需要"。

中间件和基础设施在出现对应问题的那周再引入：

| 周 | 引入 | 先遇到的问题 |
|---|---|---|
| W1 | PostgreSQL + TypeORM + migration | 数据存在内存里，重启就没了；手动改表，换台机器表结构就对不上 |
| W2 | Zod 校验、全局异常过滤器、统一响应格式 | 传错数据直接 500；每个接口错误格式不同，前端没法统一处理 |
| W3 | JWT、全局守卫、密码哈希 | 谁都能看所有单据；每个接口手写登录检查，漏一个就是漏洞 |
| W4 | refresh token + 无感刷新、RBAC 权限守卫 | token 一过期就掉线；普通员工能直接调用审批接口 |
| W5 | 事务、乐观锁（更新前确认没被别人改过）、审批记录 | 审批要同时写多张表，写一半失败；两人同时审批同一张单 |
| W6 | 请求 ID + 结构化日志、拦截器、限流、幂等键 | 报错查不到是哪个请求；有人暴力试密码；连点两次提交出两张单 |
| W7 | 文件上传（先存本地磁盘）、SSE 推送 | 报销要附发票；审批结果要马上通知申请人 |
| W8 | Nginx 反向代理 + 两个 API 实例；Redis（限流计数、token 黑名单、发布订阅、分布式锁）；定时任务 | 两个实例后：限流各算各的；一台退出登录，token 在另一台还能用；定时提醒发两遍；通知推不到连在另一台上的用户；附件只在一台上 |
| W9 | SQL 聚合与索引、Redis 缓存、BullMQ 队列 + 独立 worker 进程 | 造 100 万条数据后列表和报表变慢；导出大 Excel 时请求超时 |
| W10 | Docker + compose、Nginx 网关进阶（HTTPS、gzip、网关限流、请求 ID）、对象存储 | "我电脑上能跑"，换台机器跑不起来；W8 遗留的附件问题 |
| W11 | GitHub Actions、Playwright、安全加固 | 手动检查容易忘；改了 A 坏了 B 没人发现 |
| W12 | 结构化输出、RAG（pgvector）、流式输出 | 填单太繁琐；制度文档没人看 |

本机现状（2026-10-27 核对）：PostgreSQL 18.6、Redis 8.10.2 已通过 Homebrew 安装；Node 由 Volta 管理；没有 Docker 和 Nginx（W8 用 Homebrew 装 Nginx，W10 装 OrbStack 或 Colima）。

几个关键选择的倾向（由作者在对应那周写成 ADR）：

- 认证用 JWT 双 token：access token 短期、只放内存；refresh token 放 HttpOnly Cookie 且每次刷新都轮换；退出时把 access token 放进 Redis 黑名单（W8）。
- 实时通知用 SSE，不用 WebSocket：只需要服务端单向推送，SSE 更简单，W12 的流式输出也复用它。
- 队列用 BullMQ（基于 Redis），不用 Kafka/RabbitMQ：单体应用的异步任务，用现成的 Redis 就够。
- 金额以"分"为单位存整数；接口里用 number 还是 string，由作者在 W2 的技术设计里决定。

## 四、13 周路线

结构参考：前后端从第 1 周一起写、尽早做出能用的东西（[Full Stack Open](https://fullstackopen.com/en/)）；技术点跟着业务模块出现（黑马「苍穹外卖」）；最后用 compose + Nginx 部署整套系统（掘金小册《Nest 通关秘籍》的会议室预订系统）。

| 周 | 浏览器里能看到的成果 | 后端重点 | 前端配对 |
|---|---|---|---|
| W1 从零跑通 | 管理员维护报销类型：列表、新增、编辑、停用 | monorepo；Nest 模块、控制器、服务、依赖注入；REST；TypeORM 实体与 migration | Ant Design 布局、表格 + 弹窗表单、Vite 代理 |
| W2 报销单草稿 | 员工新建报销单（多条明细），分页筛选、详情、编辑 | 一对多关系、事务入门、Zod 校验、统一错误码、分页；第一批连真实数据库的接口测试 | 请求层封装、统一错误提示、自动生成接口类型、动态明细行 |
| W3 登录与鉴权 v1 | 登录页；员工只看到自己的单据 | 密码哈希、JWT、全局守卫、当前用户、防越权；seed 虚构公司数据 | 路由守卫、401 跳回登录 |
| W4 双 token 与 RBAC | 刷新不掉线；不同角色菜单和按钮不同；管理员管理部门、员工、角色；首次登录改密码 | refresh token 轮换、退出、RBAC 表设计、权限守卫 | 无感刷新（并发请求排队）、菜单 / 路由 / 按钮权限 |
| W5 审批流 | 提交、主管审批、财务打款、驳回、撤回；审批时间线；待我审批 | 状态机、数据权限、事务、乐观锁、单号生成 | 审批工作台、时间线、按状态和权限显示按钮 |
| W6 请求链路 | 报错带错误编号；登录被限流；连点提交只生成一张 | 中间件 → 守卫 → 拦截器 → 管道 → 过滤器全链路；请求 ID、结构化日志、操作日志、限流、幂等 | 错误编号展示、幂等键、防重复提交 |
| W7 附件与通知 | 上传并预览发票；审批结果实时通知、未读数 | 文件上传与安全校验、SSE、站内信 | 上传组件（进度、预览）、通知中心 |
| W8 多实例与 Redis | Nginx 后面跑两个 API 实例，功能依然正确；超时未审批自动提醒 | Nginx 反向代理与负载均衡、无状态服务、Redis、定时任务与分布式锁 | SSE 断线重连 |
| W9 报表与性能 | 统计看板；百万数据下依然快；异步导出 Excel | SQL 聚合与时区、EXPLAIN 与索引、缓存与失效、BullMQ + worker | ECharts 看板、导出进度 |
| W10 容器化与网关 | 一条命令起整套系统；HTTPS 访问；附件存对象存储 | Docker 多阶段构建、compose 编排、Nginx 网关、对象存储、部署时单独执行 migration | 生产构建、静态资源缓存 |
| W11 质量与 CI/CD | 每个 PR 自动检查；主流程端到端测试；越权请求全部被拦 | GitHub Actions、分层测试、安全加固（安全头、CORS、依赖扫描） | Playwright 端到端测试 |
| W12 AI | 拍发票自动预填明细；制度问答带引用、流式输出 | 结构化输出、RAG + pgvector、超时 / 限流 / 成本控制、防提示注入 | 流式渲染、确认后才填入 |
| W13 收官 | 文档、架构图、演示视频；模拟面试 | 按企业级清单整体复查 | — |

里程碑：

- W4 末：系统雏形，能登录，不同角色看到不同的菜单和数据。
- W6 末：核心业务跑通，报销单能从提交走到打款，请求链路达到企业级；从这里开始项目可以拿去讲。
- W10 末：面试最常问的内容全部完成，包括部署。
- W13 末：完整交付。

面试准备贯穿全程：每周 5～8 道对应的面试题，作者作答、助手批改，13 周累积成自己的题库；W13 由助手扮演面试官，围绕这个项目连续追问。

缓冲和取舍：

- 某周没做完就顺延，不跳过，也不熬夜补。
- 需要压缩时，先砍 W12 两个 AI 功能中的一个，再压缩 W13；W1～W11 的主线不砍。
- 算法不在每周 15 小时内；目标公司考算法的话，每周另加 2～3 小时。

选修（主线完成后或面试间隙）：按金额分级的可配置审批流、多层级部门树、多公司 SaaS（多租户）、GitHub 第三方登录、前端监控、用 RN 做移动端审批 App（复用同一套 API）。

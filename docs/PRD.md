# 产品需求｜星河报销（企业费用报销系统）

- 版本：v2.1（2026-10-28，补全审批人、通知、可见范围和校验时机等规则）。v2.0 起取代上一版个人账本 PRD，旧版见 tag `v1-backend-first`
- 性质：全栈学习项目，只用虚构数据；不是真实的财务系统
- 用法：这里定义业务角色、流程和规则；每周迭代文档（`docs/plan/WNN-*.md`）再把其中一部分细化成当周的用户故事和验收标准

## 1. 背景与目标

虚构公司「星河科技」约 50 人，现在用纸质单据加 Excel 报销：单据在谁手里说不清，审批慢，财务月底要手工汇总对账，报销制度没人看。

目标是把报销全流程搬到线上：员工在线提交，审批人在线处理，进度随时可查，财务能统计和导出。

产品上的成功标准：

- 一张报销单能从创建走到打款，每一步谁、在什么时间、做了什么都能追溯。
- 每个人只能看到和操作自己权限范围内的单据。
- 财务按月份、部门、报销类型看到的统计金额，与明细逐条相加的结果一致。

## 2. 角色

| 角色 | 能做什么 |
|---|---|
| 员工 | 创建、编辑、提交、撤回自己的报销单；查看自己单据的进度；接收通知 |
| 部门主管 | 员工的全部能力；审批本部门员工的报销单；查看本部门已提交的单据和统计 |
| 财务 | 审核已通过主管审批的单据、驳回、确认打款；查看全部已提交的单据和统计；导出 |
| 系统管理员 | 维护部门、员工账号、角色权限和报销类型；查看操作日志；看不到他人的报销单，也没有审批权 |

- 每个人都是员工，可以报销自己的费用；主管、财务、管理员是在员工之上额外获得的能力，一个人可以同时有多种（例如财务部主管）。
- 财务和系统管理员是分配给账号的角色；主管不是角色，而是部门上的一项设置：管理员从本部门员工中为部门指定主管，被指定的人才能审批本部门的单据。
- 每个部门最多一位主管。部门还没有主管时，该部门员工不能提交报销单，页面提示联系管理员；主管调出本部门或账号被停用时，该部门的主管设置清空。
- 草稿只有申请人自己能看到。
- 职责分离：任何人都不能审批或打款自己提交的单据。
- 账号由系统管理员创建，没有公开注册；首次登录必须修改初始密码；停用的账号不能登录，历史单据保留。

## 3. 报销单生命周期

| 当前状态 | 动作 | 谁能做 | 之后的状态 |
|---|---|---|---|
| 草稿 | 编辑、删除 | 申请人 | 草稿 / 删除 |
| 草稿 | 提交 | 申请人 | 待主管审批；申请人本人是部门主管时直接进入待财务审核 |
| 待主管审批、待财务审核 | 撤回 | 申请人 | 草稿 |
| 待主管审批 | 通过 | 单据所属部门的主管 | 待财务审核 |
| 待主管审批 | 驳回（必须填写意见） | 单据所属部门的主管 | 已驳回 |
| 待财务审核 | 通过 | 财务（不能是申请人本人） | 待打款 |
| 待财务审核 | 驳回（必须填写意见） | 财务（不能是申请人本人） | 已驳回 |
| 待打款 | 确认打款（可批量） | 财务（不能是申请人本人） | 已打款（终态） |
| 已驳回 | 修改后重新提交 | 申请人 | 同"提交" |

- 只有草稿和已驳回的单据可以修改内容；其他状态下单据锁定。
- 只有草稿可以删除；提交过的单据（包括已驳回）不能删除，保证审批记录完整。
- 单据所属部门在每次提交（含重新提交）时，按申请人当时所在的部门确定；之后申请人调部门，不影响已提交的单据。
- 主管环节由单据所属部门的当前主管处理：主管换人后，待审批的单据转给新主管；新主管恰好是申请人本人时，不能自己审批，由申请人撤回后重新提交（主管提交直接进入待财务审核）。
- 财务环节由任意一位财务处理（申请人本人除外）。
- 每次状态变化都留下一条审批记录（操作人、动作、意见、时间），审批记录不能修改或删除。
- 表格以外的状态变化一律拒绝，例如未经审批直接打款。

## 4. 业务规则

报销单与明细：

- 报销单包含事由（1～50 字）和 1～20 条明细；每条明细包括报销类型、金额、费用发生日期、说明（最多 100 字），可附发票图片。
- 币种只有人民币，精确到分，计算过程不能使用浮点数。
- 单条明细金额 0.01～50,000.00 元；报销单总额由系统按明细计算，不接受前端传入的总额。
- 费用发生日期不能晚于当天，也不能早于当天往前 90 天（虚构制度，按北京时间判断）。
- 以上规则在保存草稿时就检查；提交（含重新提交）时，按提交当天再检查一次日期范围，并要求明细里没有已停用的报销类型。
- 单号格式为 `BX` + 8 位日期 + 4 位当日序号，例如 `BX202611030001`，全局唯一；首次提交时按北京时间的日期生成，之后重新提交不变。

报销类型：

- 由系统管理员维护：名称（1～20 字，首尾空格不算；不能和已有类型重名，包括已停用的）、说明（最多 100 字）、启用状态。
- 类型不能删除，只能停用和重新启用；停用的类型不能用于新的明细，已有单据照常显示。单据按类型的 ID 关联，类型改名后，历史单据也显示新名称。

组织与账号：

- 部门只有一层，没有子部门。
- 每个员工属于一个部门；调整部门只影响之后提交的单据。

通知：

- 单据进入待审批状态时（提交、重新提交、主管通过），通知这一环节的审批人：主管环节通知部门主管，财务环节通知所有财务（申请人本人除外）。
- 通过、驳回、打款后，通知申请人。
- 单据停在待审批状态（待主管审批或待财务审核）超过 24 小时，每天北京时间 9:00 提醒这一环节的审批人一次。

统计与导出：

- 统计已打款单据的金额和笔数：按打款时间所在的自然月（北京时间）归属；按部门统计用单据所属部门；按报销类型统计时，金额和笔数都按明细算。另外展示各状态的单据数量。
- 数据范围：财务看全部，主管看本部门，员工看自己。
- 财务可按筛选条件导出 Excel；超过 1,000 条时转为后台生成，完成后通知下载。

AI（第 12 周）：

- 发票识别：上传发票图片后识别金额、日期并建议报销类型，申请人确认后才填入明细，不会自动提交。
- 制度问答：根据虚构的《星河科技费用报销制度》回答，附上引用的条款；制度里没有的内容明确回答"制度中没有相关规定"，不回答与报销无关的问题。
- AI 只能读取当前用户有权看到的数据，不能提交、审批或打款。

## 5. 非功能需求（目标值，在对应周验证；实测后可以修正）

- 安全：密码只存哈希；权限在后端校验，前端隐藏按钮只是体验；越权请求拿不到数据；登录有频率限制；日志不记录密码、token 和发票内容。
- 可靠：重复提交不会产生重复的单据或审批记录；同一张单的并发操作（两人同时审批、撤回和审批同时发生）只有一个成功；多实例部署时功能一致，定时提醒不重复发送。
- 性能：100 万张报销单（约 300 万条明细）时，本机测试列表接口 P95 低于 200 ms；统计接口不走缓存时低于 1 s，命中缓存时低于 50 ms。
- 可观测：每个请求有请求 ID，从前端的错误提示、Nginx 日志到 API 日志都能用它串起来。
- 浏览器：桌面端最新版 Chrome、Edge、Safari。

由 seed 脚本生成一家虚构公司：研发部、市场部、财务部、行政部 4 个部门，约 50 名员工，覆盖全部角色，其中财务至少 2 人（财务自己的单据要由另一位财务审核）。演示账号的密码在运行 seed 时从命令行提供，不写进代码和文档。

AI 功能用的发票图片是自己制作的虚构样张：图片会发送给模型服务商，不能用真实发票。

## 7. 不做

真实支付与银行接口、发票验真、电子签章、多公司（多租户）、可配置的多级审批流、移动端 App、公开注册。其中多租户、可配置审批流和移动端 App 列为选修（见总计划）。
